# solver 構成の追補 — dense 表現への切替 — **結果を見る前に凍結** — 2026年9月18日

前提：SOLVER_SPEC_World1G（f6c1ad0 → 503d2f4 → a66e9e4）
経緯：到達可能集合の規模測定で、(1) macro を状態ごとに辿る実装が重複で遅い、(2) primitive global propagation で946倍になり support は完全一致、(3) その版は Python の集合表現でメモリが壁（t=51 で RSS 8GB）と分かった。

**これは近似ではない。状態の表現方法を変えるだけ。** 確率の打ち切り・標本化・粗視化・状態の集約は一切入れない。

## 1. 決めること

1. **primitive な1歩 MDP を solver の正本候補とする**（「候補」と書くのは、dense 版と tuple/set 版の一致確認が済むまで確定しないため。一致したら正式採用）
2. 状態は**固定 index の dense 表現**（bool マスク／値の配列）
3. reachability は current / next の**2層**のマスク
4. 後ろ向き帰納も current / next の**2層**（primitive なら常に t → t+1 なので101層は不要）
5. **終端は未来の frontier に保持しない**
6. D1a の48条件は**最初は1条件ずつ**解く（同時に持つとメモリが増える。速度より正しさ）
7. tuple/set 版との **count と SHA-256 digest の一致を必須の検証**とする
8. **RSS watchdog（8GB）を外側から常時使う**（`watchdog_run.py`。2026/9/18 に試験済み：上限1.0GB に対し 1.09GB で0.8秒後に停止）

**dense を選ぶ理由**：状態空間の理論上限が既知で、**メモリ使用量を事前に上限評価できる**から。飽和の予想を理由にしない（飽和するかは t=50 までしか測れていない）。

## 2. MODE の実測（2026/9/18）

定義は9種類だが、**frontier に現れるのは8種類**。`grass` は現れない（decision の歩で草を食べ、その歩の終わりに decision へ戻るため）。

```
decision / search_small / chase_1 / chase_2 / chase_3 / chase_4 / search_large / combat
```

t=0..30 の全 frontier を走査して確認した。

## 8. 追記（2026/9/18、solver 実装の前に発見）

### 8-1. 「2層で済む」のは価値の計算だけ

後ろ向き帰納の**価値**は current / next の2層で足りる。
しかし表3（6864d5b）で測ると決めたもの——方策一致率、占有率で重み付けした不一致、到達する状態の分布、迷いの三分類、絶滅の割合——は、**各時刻の方策**と、それに沿って**前向きに流した占有率**を必要とする。

**メモリの実測見積もり**

| | 値 |
|---|---|
| 方策（decision のみ、1状態1バイト）1時刻 | 1.01 MB |
| 同・1000時刻 | **0.98 GB** |
| 方策（primitive 全体）1000時刻 | 7.87 GB（危険） |
| 価値 float64（primitive）1層 | 64.5 MB |
| 同・2層 | 129.0 MB |
| 占有率 float64（primitive）2層 | 129.0 MB |

**決めること（凍結）**
- **方策は decision 状態についてのみ、全時刻をメモリに保持する（0.98GB）。** primitive 状態の方策は保持しない（強制 MODE には選択がないため不要）
- 後ろ向きで価値と方策を解いたあと、**前向きにもう一度流して占有率を計算する**（2パス）
- 占有率も current / next の2層
- 1条件あたりの合計見積もり：方策 0.98GB + 価値 0.13GB + 占有率 0.13GB + マスク類 ≈ **1.3GB 前後**。8GB の上限には収まる見込み（推測。実測で確かめる）
- D1a の48条件は1条件ずつ解く（6864d5b のとおり）。方策を条件ごとに保存するならディスクへ

### 8-2. 飢え死の歩の体力は負の値をそのまま使う

`world1g.py` は飢え死の歩に負の体力を保持する（334歩目で 2000 − 6×334 = −4）。
**表2 の D1a は、この負の値をそのまま使って D を計算する。0 に切らない。**
範囲は最大でも −70（1歩の消耗の上限 20 + 5×10）〜 −1。
※ここを 0 に切ると結果が変わるので、実装で勝手に切らないこと。

**dense の index への影響**：体力の軸は 0..2000 の2001枠しかない。負の体力は**終端状態にしか現れない**ので、終端を frontier に入れない現在の方式では index に含める必要がない。D1a の報酬計算のときだけ、終端の体力を別に持つ。

### 8-3. 傷のあふれ K は消耗も過小評価する

W ≥ K を一つのあふれ状態にまとめると、**その状態の1歩の消耗も 20 + 5×K で頭打ちになる**。
本当は W=12 なら消耗80だが、K=10 のあふれでは70として扱われる。
**これは「状態数を有限にする近似」であると同時に「消耗を過小評価する近似」でもある。**
K の収束確認（10 → 12 → 15）で、あふれの質量・初期状態の価値・optimal_set・主要な不一致が動かないことを見る（6864d5b のとおり）。

### 8-4. MODE=8 は定義から出る（観測ではなく）

v02 §1-2：decision は時間を使わない境界で、選んだ行動の1歩目を同じ歩で実行する。
v02 §1-4：草は1歩の行動で、その歩の終わりに decision へ戻る。
→ **`grass` は歩の途中の状態として存在しない。** frontier に現れる MODE は
`decision / search_small / chase_1..4 / search_large / combat` の8種類。
終端（飢え死・急所死・天寿）は未来の frontier に入れない（a66e9e4）。

### 8-5. dense の index（凍結）

```
i = ((((m * 2001 + e) * 11 + w) * 12 + (n_small - 1)) * 4 + n_large)

m  : decision=0, search_small=1, chase_1=2, chase_2=3, chase_3=4,
     chase_4=5, search_large=6, combat=7
e  : 0..2000（2001枠。負の体力は終端にしか現れないので含めない）
w  : 0..10（★11枠目の index 10 は「W ≥ 10 のあふれ」であって「ちょうど10」ではない★）
n_small : 1..12 を index 0..11 に写す
n_large : 0..3
```

合計 8 × 2001 × 11 × 12 × 4 = **8,452,224**

## 9. 追記2（2026/9/18、冷監査の前に。ChatGPT 返答66 の指摘）

### 9-1. 傷のあふれ K は、消耗だけでなく**治癒の仕組みそのもの**を近似する

正本では 1歩に治る傷の数は **Binomial(W, 1/150)**。つまり**治癒の確率が W に依存する**。
あふれで W ≥ K を代表値 K として扱うと、**3方向にずれる**（K=10、真の W=12 の場合）。

| | 真（W=12） | 代表（W=10） | ずれ |
|---|---|---|---|
| 1歩の消耗 | 80 | 70 | **−12.5%** |
| 1歩の期待治癒数 | 0.08000 | 0.06667 | **−16.7%** |
| 1歩で1個以上治る確率 | 0.07713 | 0.06470 | −16.1% |

さらに**あふれからの脱出時刻が変わる**：
```
真   W=12 → 1個治癒 → W=11 → まだあふれ
代表 W=10 → 1個治癒 → W=9  → あふれを脱出
```

**したがって K のあふれは「状態を有限にする近似」であると同時に、**
**「消耗を過小評価し、治癒を過小評価し、あふれからの脱出を早める非マルコフ的な集約」である。**

**K=10 → 12 → 15 の収束検査は、消耗の近似だけでなく、この集約全体への感度検査と定義する。**
測るもの（6864d5b のとおり）：あふれの質量 P(W≥K)、初期状態の価値 V、初期状態の optimal_set、主要な占有率重み付き不一致。

あふれに入る頻度の目安（計算）：1回の大物狩りの期待負傷 1.2414、治癒は平均150歩、1回の狩りは平均11.45歩。150歩で最大13回の狩りができるので、**同時に10個の傷を抱えることは起こりうるが稀**。実測で質量を測る。

### 9-2. 方策だけでは表3 を復元できない

表3 には「上位2行動の価値の差」「行動価値の開き」「迷いの三分類」がある。
**これらは方策からは復元できない。**

```
grass Q=10.000 / small Q=9.999   → 選ばれた行動は同じ
grass Q=10.000 / small Q=2.000   → 意味は全く違う
```

**決めたこと（凍結）：後ろ向きの計算の途中で、必要な派生量だけを保存する。**
Q そのもの（3本）は保存しない。保存するのは decision 状態ごとに：

| 保存するもの | 型 | 1条件あたり |
|---|---|---|
| 方策 selected_for_execution | 1バイト | 0.98 GB |
| optimal_set（3行動をビットで） | 1バイト | 0.98 GB |
| 上位2行動の価値の差 | float16 | 1.97 GB |
| 行動価値の開き（1位−3位） | float16 | 1.97 GB |
| 上位2行動の即時死亡確率の差 | float16 | 1.97 GB |
| **合計** | | **約7.9 GB** |

float32 なら13.78GB。**float16 を使う**（迷いの三分類は分布の形を見るので、この精度で足りる。ただし二値化の閾値を後から選ばない方針は変えない）。

### 9-3. 48条件を全部保存しない

**D1a の48条件を全部保存すると 7.9GB × 48 = 約661GB。現実的でない。**

**運用（凍結）**
```
1条件を解く
  → 方策と派生量をメモリ／memmap に持つ
  → 前向きに流して占有率を出し、表3 を集計する
  → ★要約だけをディスクに残す★（分布のヒストグラム、集計値、digest）
  → 次の条件へ
```
全条件の生データは保持しない。**要約に何を含めるかは、結果を見る前に固定する**（表3 の項目そのもの）。

### 9-4. 終端の負の体力について、回帰テストを置く

仕様に書くだけでなく、テストで固定する。

```
E=2 の状態 → 消耗20 → 終端 E=−18
→ D1a の報酬が E=0 ではなく E=−18 を使って計算されることを確認する
```

これを solver の検証に加える（**post-diagnostic ではなく、実装前に登録するテスト**）。

### 10-1. 両監査が突いた箇所（2件）

**(A) D1a には、死によって将来の負の報酬を打ち切る構造的な誘因がある**

計算で確認（γ=0.999、q=2、体力1900で急所死する価値 対 体力1900のまま500歩生きる価値）：

| E_set | 急所死 | 生存500歩 | |
|---|---|---|---|
| 2000 | −4,400 | 0 | 生きる方が高い |
| 1600 | +11,600 | 0 | 死ぬ方が高い |
| 1400 | +19,600 | 0 | 死ぬ方が高い |
| 1200 | +27,600 | 0 | 死ぬ方が高い |

**★言えること：有限エピソードの D1a には、死亡によって将来の負の報酬を打ち切れる構造的な終了誘因が存在する（数学的に確定）★**
**★言えないこと：死亡が最適方策である（未確定）★**
比較したのは1本の生存軌跡だけ。他の生存方策が +11,600 を超える可能性は残る。**Bellman を解いて初めて分かる。**

**処理（凍結）：D1a は修理しない。** 任意の死亡罰を足すと、調べている目的関数そのものが変わるため。
D1a は「**有限エピソードにおける素の drive-reduction 目的**」として明示して残す。
結果の解釈を「恒常性一般の性質」に広げない。言えるのは「**この終端規約を持つ World_1-G 上で、この目的がどの方策を誘導するか**」だけ。

**代わりに対照条件を追加する（凍結）**

**D1b — terminal encoding sensitivity control**
- 物理世界は一切変えない
- **不利な死（飢え死・急所死）の歩の報酬計算だけ**、終端の体力を 0 として `r = D(E_t) − D(0)` を使う
- **天寿には適用しない**
- D1a（生の体力を保持）と D1b（死を体力0として評価）の違いだけを見る
- 「D1a の修正版」とは呼ばない。**終端表現への依存を直接測る対照条件**
- 条件数：D1b も q 3 × E_set 4 × γ 4 = 48。合計96条件になる（1条件ずつ解く運用は変えない）

**(B) 傷のあふれ K=10 の系統誤差**（両監査が指摘）

「無敵化」という表現は使わず、具体的に書く。W ≥ K を代表値 K として扱うことで：
1. 傷の消耗を過小評価する（真 W=12 で 80 → 70、−12.5%）
2. **あふれ中は追加の傷の限界コストが消える**
3. 治癒の分布が真の W と異なる（期待治癒数 0.08000 → 0.06667、−16.7%）
4. あふれから通常領域へ早く戻りうる（真 W=12→11 はあふれのまま／代表 W=10→9 は脱出）

K = 10 → 12 → 15 は**あふれ集約全体の収束感度検査**と定義する（§9-1 のとおり）。

### 10-2. 確定的な誤り（結果前に修正。私が検証済み）

**(C) float16 は使わない。** float16 の最大値 65,504 に対し、D1a の報酬は最大 −79,600。**保存した瞬間に inf になる。**
→ **Q・差・同点判定の計算はすべて float64。** 保存も float64 とし、容量はチャンク処理とディスクへの逐次書き出しで解決する。精度を落とすなら、それ自体を別途仕様化する（現時点では落とさない）。

**(D) 1条件あたりの派生量をメモリに持たない。** float64 だと1条件で 27.5GB（方策1B + optimal_set 1B + 差3本×8B ＝ 26B/状態 × 10.6億）。**メモリに全部を置くことは不可能。**
→ 運用（凍結）：
```
1条件を後ろ向きに解く
  → 方策と派生量をチャンクごとにディスクへ書き出す（memmap／逐次 flush）
  → 前向きに流して占有率を出す
  → 表3 を集計する
  → ★要約だけ残し、一時ファイルを削除する★
  → 次の条件へ
```
**memmap なら RSS を消費しないとは仮定しない**（OS のページキャッシュで常駐しうる）。チャンク処理・flush・外側の watchdog 8GB を維持する。

**(E) 草の「正味 −6/歩」は W=0 のときだけ。** 正しくは **14 − (20 + 5W) = −6 − 5W**（W=10 なら −56）。**仕様書の記述が誤り**（コードは正しい）。

**(F) N_L=1 で仕留めと回復が同時のとき、肉は得る。** コードで確認（体力 100 → 1880）。**順序を仕様に明記する**：
```
仕留め成立 → 摂取 +1800 → N_L = 0 → 回復は無効 → 絶滅
★絶滅する最後の1頭からも栄養は得る★
```

**(G) τ_max と rolling buffer 101本は macro 時代の記述。** 現在の正本は1歩 MDP なので不要。
→ **a66e9e4 の該当部分を SUPERSEDED と明記する**（Git 履歴からは消さない）。**τ_max=100 という物理的事実自体は残す**（macro kernel を作る場合に必要）。

**(H) 危険度の定義を3排他事象にする。**
```
P_danger(s,a) = P(不利な死 | s,a)
排他的な3事象：不利な死 ／ 生きて次の decision に戻る ／ 天寿に到達
分母は1（全事象）
```
終盤に天寿ルートが混ざっても分母が崩れない。

**(J) δ を選ばない。**

「迷い」の三分類は**二次的な分類**に落とし、**複数の δ を事前に固定したグリッドで全部報告する**（単一の δ を結果の後から選ばない）。
危険度の差 ΔP_danger も、まず連続量として残す。

### 10-3. 監査の指摘を採用しなかったもの

**(I) 同点判定 atol=1e-9 は機能しないという指摘 → 採用しない。**
判定式は `|Qa − Qb| ≤ atol + rtol · max(1, |Qa|, |Qb|)` で、**rtol がスケールに追従している**。検算：

| Q のスケール | 実際の閾値 |
|---|---|
| 1 | 1.001e−09 |
| 1,000 | 2.000e−09 |
| 1,000,000 | **1.001e−06** |
| 100,000,000 | 1.000e−04 |

監査は atol だけを見て批判しており、**rtol 項を読み落としている。**
→ **バグとは認定しない。** float64 で独立実装の一致を確認し、それでも数値ノイズが 1e−6 を超えるなら再検討する。
→ **書記官の反省**：この指摘を検算せずに受け入れかけた。ChatGPT が訂正した。

### 10-4. 結果を見た後で考察するもの（監査が「後でよい」としたもの）

- **γ の交絡**：D0 と D_S-exact は γ=1、D1a だけ γ<1。行動の違いが「目的のせい」か「近視眼のせい」か分離できない。γ=1 の恒常性モデルという対照群がない
- **校正世界のバイアス**：D0 基準で拮抗を作った世界が、D1a にとっても拮抗する保証はない
- **寿命終盤の境界効果**：t=990 で負った傷は最大50しか奪わないが、t=10 の傷は期待値750を奪う。**終盤に全ての目的が好戦的になる**。これは生態学的な最適ではなく「世界の終わりを知っていることによるアーティファクト」。記述統計では「定常状態の振る舞い」と「終端効果」を分けて解釈する

### 16-3. MODE ごとの内訳と、**structural-valid と reachable の分離**

**この2つは別概念。混同しない。**
- **structural-valid**：その MODE で**物理的に存在し得る**状態。**時刻に依存しない**
- **reachable**：初期状態から、その時刻に**到達できる**状態。**時刻に依存する**

| MODE | 到達可能 | 到達不能 | うち構造的に存在しない | 存在するが到達不能 |
|---|---|---|---|---|
| decision | 1,055,659 (99.92%) | 869 | 0 | 869 |
| search_small | 1,032,240 (97.70%) | 24,288 | 0 | 24,288 |
| chase_1 | 1,032,240 (97.70%) | 24,288 | 0 | 24,288 |
| chase_2 | 1,008,480 (95.45%) | 48,048 | 0 | 48,048 |
| chase_3 | 984,720 (93.20%) | 71,808 | 0 | 71,808 |
| chase_4 | 960,960 (90.95%) | 95,568 | 0 | 95,568 |
| search_large | 774,180 (73.28%) | 282,348 | **264,132** | 18,216 |
| combat | 774,180 (73.28%) | 282,348 | **264,132** | 18,216 |
| **合計** | **7,622,659** | **829,565** | **528,264 (63.7%)** | **301,301** |

**構造的に存在しない 528,264 の正体**：`search_large + N_L=0` と `combat + N_L=0`（各 264,132 = 1,056,528 ÷ 4）。**大物が0頭なら大物探索も戦闘も存在しない。**

**829,565 を全部「invalid」と呼ばない。** 63.7% は構造外、36.3% は到達できないだけ。

### 16-4. solver の表現（**ここまでは凍結**）

- **価値：primitive の dense 配列**（8,452,224 × float64 = 67.6MB／層。2層で135MB）
- **方策：decision の dense 配列**（1,056,528 × 1000時刻 × 1バイト = 0.98GB）
- **decision の疎な表現（辞書など）は採用しない**（99.92% が埋まるため）
- **structural-invalid（時刻に依存しない）はマスクの候補**
- **時刻ごとの reachability による高速化は、まだ solver 正本に固定しない**

**固定点の reachable マスクを、全時刻の valid マスクとみなさない。** t=0..118 では本来到達不能な状態が大量にあるので、固定点のマスクを全時刻に使っても計算量は減らない。逆に各時刻のマスクを全部保存するとメモリを使う。**どれが有利かは縮小世界と性能の検証で決める。**

### 16-5. support fixed point は価値の定常性を意味しない

**定常になったのは「全行動を許したときの support-reachable な状態集合」だけ。**

**定常でないもの**：最適方策、価値、占有率、死亡確率、資源の分布、行動選択。有限寿命なので V_t(s) ≠ V_{t+1}(s) が普通に起きる。
**t=119 以降も、後ろ向きの Bellman 計算を省略できない。**

### 16-6. 次の壁は計算量

primitive 直積 8,452,224 × 1000時刻 = **84.5億 state-time**（1条件あたり）。
D1a + D1b で96条件。**Python で状態ごとに canonical transition を呼ぶ solver は現実的でない可能性が高い。**

ただし、強制 MODE には行動の選択がなく、decision だけが3行動。ベクトル化の余地と、条件間で遷移構造を共有できる余地がある。**急いでベクトル化した物理を書かない。まず縮小世界で正しさを確かめる。**
