# solver 構成の追補 — dense 表現への切替 — **結果を見る前に凍結** — 2026年9月18日

前提：SOLVER_SPEC_World1G（f6c1ad0 → 503d2f4 → a66e9e4）
経緯：到達可能集合の規模測定で、(1) macro を状態ごとに辿る実装が重複で遅い、(2) primitive global propagation で946倍になり support は完全一致、(3) その版は Python の集合表現でメモリが壁（t=51 で RSS 8GB）と分かった。

**これは近似ではない。状態の表現方法を変えるだけ。** 確率の打ち切り・標本化・粗視化・状態の集約は一切入れない。

## 1. 決めること

1. **primitive な1歩 MDP を solver の正本候補とする**（「候補」と書くのは、dense 版と tuple/set 版の一致確認が済むまで確定しないため。一致したら正式採用）
2. 状態は**固定 index の dense 表現**（bool マスク／値の配列）
3. reachability は current / next の**2層**のマスク
4. 後ろ向き帰納も current / next の**2層**（primitive なら常に t → t+1 なので101層は不要）
5. **終端は未来の frontier に保持しない**
6. D1a の48条件は**最初は1条件ずつ**解く（同時に持つとメモリが増える。速度より正しさ）
7. tuple/set 版との **count と SHA-256 digest の一致を必須の検証**とする
8. **RSS watchdog（8GB）を外側から常時使う**（`watchdog_run.py`。2026/9/18 に試験済み：上限1.0GB に対し 1.09GB で0.8秒後に停止）

**dense を選ぶ理由**：状態空間の理論上限が既知で、**メモリ使用量を事前に上限評価できる**から。飽和の予想を理由にしない（飽和するかは t=50 までしか測れていない）。

## 2. MODE の実測（2026/9/18）

定義は9種類だが、**frontier に現れるのは8種類**。`grass` は現れない（decision の歩で草を食べ、その歩の終わりに decision へ戻るため）。

```
decision / search_small / chase_1 / chase_2 / chase_3 / chase_4 / search_large / combat
```

t=0..30 の全 frontier を走査して確認した。

dense で持っても、毎時刻845万状態を Python のループで舐めたら時間で死ぬ。
**NumPy のベクトル化された更新**を基本にする。到達可能マスク（valid mask）で無効な状態を落とす。

## 8. 追記（2026/9/18、solver 実装の前に発見）

### 8-1. 「2層で済む」のは価値の計算だけ

後ろ向き帰納の**価値**は current / next の2層で足りる。
しかし表3（6864d5b）で測ると決めたもの——方策一致率、占有率で重み付けした不一致、到達する状態の分布、迷いの三分類、絶滅の割合——は、**各時刻の方策**と、それに沿って**前向きに流した占有率**を必要とする。

**メモリの実測見積もり**

| | 値 |
|---|---|
| 方策（decision のみ、1状態1バイト）1時刻 | 1.01 MB |
| 同・1000時刻 | **0.98 GB** |
| 方策（primitive 全体）1000時刻 | 7.87 GB（危険） |
| 価値 float64（primitive）1層 | 64.5 MB |
| 同・2層 | 129.0 MB |
| 占有率 float64（primitive）2層 | 129.0 MB |

**決めること（凍結）**
- **方策は decision 状態についてのみ、全時刻をメモリに保持する（0.98GB）。** primitive 状態の方策は保持しない（強制 MODE には選択がないため不要）
- 後ろ向きで価値と方策を解いたあと、**前向きにもう一度流して占有率を計算する**（2パス）
- 占有率も current / next の2層
- 1条件あたりの合計見積もり：方策 0.98GB + 価値 0.13GB + 占有率 0.13GB + マスク類 ≈ **1.3GB 前後**。8GB の上限には収まる見込み（推測。実測で確かめる）
- D1a の48条件は1条件ずつ解く（6864d5b のとおり）。方策を条件ごとに保存するならディスクへ

### 8-2. 飢え死の歩の体力は負の値をそのまま使う

`world1g.py` は飢え死の歩に負の体力を保持する（334歩目で 2000 − 6×334 = −4）。
**表2 の D1a は、この負の値をそのまま使って D を計算する。0 に切らない。**
範囲は最大でも −70（1歩の消耗の上限 20 + 5×10）〜 −1。
※ここを 0 に切ると結果が変わるので、実装で勝手に切らないこと。

**dense の index への影響**：体力の軸は 0..2000 の2001枠しかない。負の体力は**終端状態にしか現れない**ので、終端を frontier に入れない現在の方式では index に含める必要がない。D1a の報酬計算のときだけ、終端の体力を別に持つ。

### 8-3. 傷のあふれ K は消耗も過小評価する

W ≥ K を一つのあふれ状態にまとめると、**その状態の1歩の消耗も 20 + 5×K で頭打ちになる**。
本当は W=12 なら消耗80だが、K=10 のあふれでは70として扱われる。
**これは「状態数を有限にする近似」であると同時に「消耗を過小評価する近似」でもある。**
K の収束確認（10 → 12 → 15）で、あふれの質量・初期状態の価値・optimal_set・主要な不一致が動かないことを見る（6864d5b のとおり）。

### 8-4. MODE=8 は定義から出る（観測ではなく）

v02 §1-2：decision は時間を使わない境界で、選んだ行動の1歩目を同じ歩で実行する。
v02 §1-4：草は1歩の行動で、その歩の終わりに decision へ戻る。
→ **`grass` は歩の途中の状態として存在しない。** frontier に現れる MODE は
`decision / search_small / chase_1..4 / search_large / combat` の8種類。
終端（飢え死・急所死・天寿）は未来の frontier に入れない（a66e9e4）。

### 8-5. dense の index（凍結）

```
i = ((((m * 2001 + e) * 11 + w) * 12 + (n_small - 1)) * 4 + n_large)

m  : decision=0, search_small=1, chase_1=2, chase_2=3, chase_3=4,
     chase_4=5, search_large=6, combat=7
e  : 0..2000（2001枠。負の体力は終端にしか現れないので含めない）
w  : 0..10（★11枠目の index 10 は「W ≥ 10 のあふれ」であって「ちょうど10」ではない★）
n_small : 1..12 を index 0..11 に写す
n_large : 0..3
```

合計 8 × 2001 × 11 × 12 × 4 = **8,452,224**

## 9. 追記2（2026/9/18、冷監査の前に。ChatGPT 返答66 の指摘）

### 9-1. 傷のあふれ K は、消耗だけでなく**治癒の仕組みそのもの**を近似する

正本では 1歩に治る傷の数は **Binomial(W, 1/150)**。つまり**治癒の確率が W に依存する**。
あふれで W ≥ K を代表値 K として扱うと、**3方向にずれる**（K=10、真の W=12 の場合）。

| | 真（W=12） | 代表（W=10） | ずれ |
|---|---|---|---|
| 1歩の消耗 | 80 | 70 | **−12.5%** |
| 1歩の期待治癒数 | 0.08000 | 0.06667 | **−16.7%** |
| 1歩で1個以上治る確率 | 0.07713 | 0.06470 | −16.1% |

さらに**あふれからの脱出時刻が変わる**：
```
真   W=12 → 1個治癒 → W=11 → まだあふれ
代表 W=10 → 1個治癒 → W=9  → あふれを脱出
```

**したがって K のあふれは「状態を有限にする近似」であると同時に、**
**「消耗を過小評価し、治癒を過小評価し、あふれからの脱出を早める非マルコフ的な集約」である。**

**K=10 → 12 → 15 の収束検査は、消耗の近似だけでなく、この集約全体への感度検査と定義する。**
測るもの（6864d5b のとおり）：あふれの質量 P(W≥K)、初期状態の価値 V、初期状態の optimal_set、主要な占有率重み付き不一致。

あふれに入る頻度の目安（計算）：1回の大物狩りの期待負傷 1.2414、治癒は平均150歩、1回の狩りは平均11.45歩。150歩で最大13回の狩りができるので、**同時に10個の傷を抱えることは起こりうるが稀**。実測で質量を測る。

### 9-2. 方策だけでは表3 を復元できない

表3 には「上位2行動の価値の差」「行動価値の開き」「迷いの三分類」がある。
**これらは方策からは復元できない。**

```
grass Q=10.000 / small Q=9.999   → 選ばれた行動は同じ
grass Q=10.000 / small Q=2.000   → 意味は全く違う
```

**決めたこと（凍結）：後ろ向きの計算の途中で、必要な派生量だけを保存する。**
Q そのもの（3本）は保存しない。保存するのは decision 状態ごとに：

| 保存するもの | 型 | 1条件あたり |
|---|---|---|
| 方策 selected_for_execution | 1バイト | 0.98 GB |
| optimal_set（3行動をビットで） | 1バイト | 0.98 GB |
| 上位2行動の価値の差 | float16 | 1.97 GB |
| 行動価値の開き（1位−3位） | float16 | 1.97 GB |
| 上位2行動の即時死亡確率の差 | float16 | 1.97 GB |
| **合計** | | **約7.9 GB** |

float32 なら13.78GB。**float16 を使う**（迷いの三分類は分布の形を見るので、この精度で足りる。ただし二値化の閾値を後から選ばない方針は変えない）。

### 9-3. 48条件を全部保存しない

**D1a の48条件を全部保存すると 7.9GB × 48 = 約661GB。現実的でない。**

**運用（凍結）**
```
1条件を解く
  → 方策と派生量をメモリ／memmap に持つ
  → 前向きに流して占有率を出し、表3 を集計する
  → ★要約だけをディスクに残す★（分布のヒストグラム、集計値、digest）
  → 次の条件へ
```
全条件の生データは保持しない。**要約に何を含めるかは、結果を見る前に固定する**（表3 の項目そのもの）。

### 9-4. 終端の負の体力について、回帰テストを置く

仕様に書くだけでなく、テストで固定する。

```
E=2 の状態 → 消耗20 → 終端 E=−18
→ D1a の報酬が E=0 ではなく E=−18 を使って計算されることを確認する
```

これを solver の検証に加える（**post-diagnostic ではなく、実装前に登録するテスト**）。
